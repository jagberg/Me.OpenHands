What each part of the factory is responsible for, independent of the tools. A ticket moves down through the layers; people sit at the two gates.

Setup steps

Setup and lifecycle, in order

1

Run Temporal in Docker

One container: the Temporal dev server with its Web UI, saving to SQLite in a Docker volume so runs survive restarts.

cd blueprint
docker compose up -d temporal          # gRPC :7233, UI http://localhost:8233
Where: blueprint/docker-compose.yml · production would use Temporal's Postgres deployment or Temporal Cloud
2

Start the worker and choose the model

The worker registers the workflow and its activities on the ignite task queue. The model is three environment variables; nothing else changes for Bedrock.

uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -r requirements.txt   # openhands-sdk, openhands-tools, temporalio

# local (today)                         # Bedrock (later, untested)
LLM_MODEL=ollama_chat/qwen3-14b-oh      # LLM_MODEL=bedrock/<model-id>
LLM_BASE_URL=http://localhost:11434     # LLM_BASE_URL=        (empty)
                                        # AWS_REGION=…  creds from role/SSO, never a file
.venv/bin/python worker.py
Where: worker.py (registration) · activities.py (MODEL, BASE_URL) · needs your git and gh login for PRs
3

Create the issue (start a run)

A run is one Temporal workflow. Three ways in, all ending in the same call:

RunView"+ New run" button, title and description
CLI.venv/bin/python start.py ../trials/TICKET.md
HTTP (for Jira later)POST /api/briefs {title, brief, source}
await client.start_workflow(
    IgniteBlueprint.run,
    {"title": title, "brief": brief, "source": "jira|cli|dashboard",
     "cfg": {"repo": "org/repo", "workdir": ".", "test_cmd": "pytest -q",
             "protected": ["test_calc.py"], "throwaway_base": False}},
    id="ignite-20261019-093000", task_queue="ignite",
    static_summary=title, static_details=brief)     # shows in the Temporal UI
Where: start() in worker.py · cfg is per run, so one worker can serve many repos
4

Load the skills

Each stage name in the workflow maps to one Markdown file. The agent stage reads that file and sends it as the task. OpenHands' own user and public skills are switched off so they don't flood the prompt.

workflow.py   STAGES:  ignite-brief → ignite-plan → ignite-build → engineering-review → security-review → qa-review → ai-code-review
skills/       ignite-brief.md  ignite-plan.md  ignite-build.md  engineering-review.md  security-review.md  qa-review.md  ai-code-review.md

agent = Agent(llm=…, tools=[terminal, file_editor],
              agent_context=AgentContext(load_user_skills=False, load_public_skills=False))

To use your real skills: replace the files in skills/ (keep the two output contracts in step 5), or add a stage by adding a file and a line in workflow.py.

Native option, not used yet: the SDK's load_project_skills(work_dir) reads a repo's .agents/skills/ folder and its AGENTS.md, and AgentContext(skills=…) passes them in. That would let the target repo carry its own ignite skills. Untested here.
5

Set the prompts

Every agent stage sends one message built from these layers, top to bottom:

OpenHands system promptout of the box stock system_prompt.j2, untouched: tools, safety, how to work.
Stage skillours skills/<stage>.md: what this stage does and the file it must write.
Contextours working folder, test command, and any extra feedback (e.g. "tests still fail: …").
Decisions so farfrom humans every answered question and its answer.
Tickettitle and description from step 3.

Contracts the workflow depends on: reviews write .ignite/<name>.md with PASS or CONCERNS; the build adds one test per decision to test_decisions.py. The decision gate has its own short prompt (returns JSON) in decision_gate().

Where: agent_stage() and decision_gate() in activities.py · skills/*.md

7

A human answers a question

After the brief, the decision gate lists open decisions. Each becomes a blocking question and the workflow parks (no compute) until it gets an answer signal. Agents can also ask during any stage by writing .ignite/QUESTION.md.

sequenceDiagram
  participant WF as Workflow
  participant A as Agent / gate
  participant RV as RunView
  actor H as Human
  A->>WF: question q1 (blocking)
  WF->>WF: status = awaiting_decision, wait
  RV->>WF: query state (every 3s)
  RV-->>H: shows q1 with an Answer box
  H->>RV: "return 0 for an empty list"
  RV->>WF: signal answer("q1", "return 0…")
  WF->>A: plan, build run with the decision
  A->>WF: test_decisions.py pins it, checks pass

Three ways to send the answer, all the same signal:

# 1. RunView: type in the Answer box, click Answer
# 2. Temporal UI: workflow → More Actions → Send a Signal → name: answer, input: ["q1", "return 0"]
# 3. CLI (verified on this setup):
temporal workflow signal -w ignite-20261019-093000 --name answer --input '"q1"' --input '"return 0"'
Where: answer() signal and wait_for_humans() in workflow.py · POST /api/runs/<id>/answer in dashboard/server.py · notifications to Chat or Jira not built yet
8

PR, AI review, human merge

Plain code commits, pushes and opens the PR with the resolution summary. An AI review agent posts a comment. The workflow then checks the PR (1, 2, 4, 8, then every 15 minutes) until a person merges or closes it, and finishes.

Where: open_pr(), post_review(), pr_state() in activities.py · add branch protection so the agent can never merge

Not built yet
